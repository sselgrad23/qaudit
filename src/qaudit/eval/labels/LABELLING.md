# Gold-set labelling guide

This directory holds the two gold sets the project is measured against. They are separate and have different labelling tasks. Both sets were seeded with draft judgements and every row has since been hand-reviewed (`"reviewed": true`), with borderline calls settled by the decision rules below and explained in each row's `note`. New rows should be added as drafts (`"reviewed": false`) and reviewed the same way. This guide is the written rubric: what "relevant" means, what a "rubric violation" means, and how to label each set.

Nothing here is regenerated by the pipeline. These files are edited by hand, and the evaluators read them as-is.

---

## 1. Retrieval gold (`retrieval_gold.json`)

**Task.** For each support conversation (the query), list the Northwind policy passages a QA reviewer would need in order to judge whether the agent handled it correctly.

**What counts as RELEVANT.** A passage is relevant if it states the policy that governs the customer's request: the rule, step, timeframe, fee, or data-handling constraint an auditor would check the agent against. Key points:

- Relevance is about the *policy an auditor would cite*, not word overlap. `pol-cancel-fee-subscription` is relevant to "what are the penalties for breaking the contract?" even though it shares no words with the query.
- A conversation can have **more than one** relevant passage (e.g. a cancellation touches the cancellation window *and* the refund-on-cancellation rule). List all of them.
- A passage about a *neighbouring* topic an auditor would not actually cite is **not** relevant. Be strict: over-labelling relevance inflates recall and hides retriever weaknesses.
- Cross-cutting passages (e.g. `pol-data-minimisation`) are relevant only when the conversation actually touches that concern, such as a third-party invoice request or a fee check that should not require account details.

**How to label.**
1. Open `retrieval_gold.json`. Each entry has `conversation_id`, `intent`, `query`, and a draft `relevant_passages` list.
2. Read the query. Skim `src/qaudit/kb/documents.json` (the passage ids and titles are enough once the KB is familiar).
3. Correct `relevant_passages` to the exact set an auditor would need. Add or remove ids.
4. Set `"reviewed": true` and, if useful, leave a `note`.

**Format.** `relevant_passages` is a list of passage `id` strings from the KB. Order does not matter.

## 2. Judge gold (`judge_gold.jsonl`)

**Task.** For each conversation, give the correct verdict for **each of the five rubric criteria**: `pass`, `violation`, or `na` (not applicable). This is the human label the LLM-as-judge is validated against (Cohen's kappa).

**Verdicts.**
- `pass`: the response satisfies the criterion.
- `violation`: the response breaks the criterion (see each criterion's `violation_when` in `src/qaudit/rubric/criteria.json`).
- `na`: the criterion genuinely does not apply. Use sparingly. Mainly for `policy_accuracy` when the reply makes **no checkable factual claim** (a pure acknowledgement, or "let me check for you"). `intent_resolution`, `completeness` and `tone_empathy` are essentially always applicable.

**What counts as a VIOLATION, per criterion** (full text in `criteria.json`):

| Criterion | Violation when |
|---|---|
| `intent_resolution` | answers a different or generic question, or ignores part of the request |
| `policy_accuracy` | states a step / timeframe / fee / eligibility rule that contradicts the KB, or invents one |
| `completeness` | a non-answer ("refer to the terms", "get in touch") with no concrete step, or omits the key detail |
| `tone_empathy` | curt, dismissive, or robotic toward a clear complaint or upset customer |
| `compliance_safety` | asks for a password / full card number / PIN / CVV in chat, leaks a third party's data, or promises an outcome policy does not allow |

**How to label.**
1. Open `judge_gold.jsonl`. Each line is one conversation with a `labels` object (`criterion_id -> verdict`).
2. Read the conversation. The text is in `data/conversations.jsonl` (real) and `data/synthetic.jsonl` (synthetic), keyed by `conversation_id`, or print it with
   `python -c "from qaudit.eval.runner import labelled_conversations as L; print({c.id:c.render() for c in L()}['conv-0007'])"`.
3. For `policy_accuracy`, check the claim against the KB passages rather than assumption.
4. Correct each verdict, set `"reviewed": true`, and note anything borderline.

**Synthetic rows (`"source": "synthetic"`).** These were built by injecting one known violation into a real response (see `qaudit.synth`). The `note` records which criterion was injected. Two things to confirm:
- the injected criterion really reads as a `violation` after the rewrite, and
- whether the rewrite *also* trips another criterion (e.g. an over-promise is both a `compliance_safety` and a `policy_accuracy` problem). The draft labels only the injected criterion to stay conservative; add the others where they apply.

**Format.** One JSON object per line. Keep `conversation_id`, `source`, `intent`; edit `labels` and `reviewed`.

**Decision rules.** Adopted during the first review pass to keep borderline calls consistent. Rows decided by one of these say so in their `note`.

- **Generic pointers fail intent too.** A reply that answers a specific question with a generic pointer ("refer to the terms and conditions", "get in touch with support") is a `completeness` violation *and* an `intent_resolution` violation, because it stays generic where the customer asked something specific.
- **Rule A: templates are not errors.** `{{Placeholders}}` are assumed filled correctly. A navigation path worded differently from the KB (e.g. "the Billing section" vs *Your Account > Orders > Download invoice*) is `pass` for `policy_accuracy` unless it sends the customer somewhere materially wrong. Omitting a KB condition (e.g. "only while Processing") is an omission, not a contradiction.
- **Rule B: invented policy content is a violation.** A service, schedule, eligibility rule or fee that the KB does not contain (in-store pickup, a newsletter "every Friday", "refund policies vary by vendor") is a `policy_accuracy` violation even when it is not directly contradicted. UI wording is covered by Rule A, not this rule. Something the customer's own request presupposes (e.g. a "gold account" tier) is not invented by the agent.
- **Rule C: clarifying questions.** Asking the customer for more detail is a `completeness` pass only when the request genuinely lacks information needed to answer (an unspecified complaint, "a problem with my account"). When the request is clear and the KB has a self-service answer (close my account, where is my order, I want a human), asking for details instead is a stall and a `completeness` violation. `intent_resolution` stays `pass` either way, since the reply is on topic.

## Review order (used for the first pass; reuse for new rows)

1. **The 9 draft violations** (2 real, 7 synthetic). The rare class drives kappa and violation-F1 most, so these come first.
2. **Every `policy_accuracy` call.** The hardest and most subjective criterion, and where the judge's biggest disagreements sit.
3. **The retrieval rows where BM25 and dense disagree.** Relevance precision matters most there (`reports/retrieval_eval.md` shows where they differ after a run).
4. The remaining `pass` rows, mostly confirmations.
