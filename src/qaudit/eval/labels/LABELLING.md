# Gold-set labelling guide

This directory holds the two gold sets the whole project is measured against. They are **separate on purpose** and have **different labelling tasks**. Every row currently carries a **draft** judgement (`"reviewed": false`) that a human should confirm or correct — the drafts are a starting point, not ground truth. This guide is the written rubric: what "relevant" means, what a "rubric violation" means, and exactly how to sit down and label.

Nothing here is regenerated by the pipeline. Edit these files by hand; the evaluators read them as-is.

---

## 1. Retrieval gold — `retrieval_gold.json`

**Task.** For each support conversation (the query), list the Northwind policy passages a QA reviewer would need in order to judge whether the agent handled it correctly.

**What counts as RELEVANT.** A passage is relevant if it states the policy that governs the customer's request — the rule, step, timeframe, fee, or data-handling constraint an auditor would check the agent against. Key points:

- Relevance is about the *policy an auditor would cite*, not about word overlap. `pol-cancel-fee-subscription` is relevant to "what are the penalties for breaking the contract?" even though it shares no words with the query.
- A conversation can have **more than one** relevant passage (e.g. a cancellation touches the cancellation window *and* the refund-on-cancellation rule). List all of them.
- A passage about a *neighbouring* topic an auditor would not actually cite is **not** relevant. Be strict: over-labelling relevance inflates recall and hides retriever weaknesses.
- Cross-cutting passages (e.g. `pol-data-minimisation`) are relevant only when the conversation actually touches that concern — e.g. a third-party invoice request, or a fee check that shouldn't require account details.

**How to label.**
1. Open `retrieval_gold.json`. Each entry has `conversation_id`, `intent`, `query`, and a draft `relevant_passages` list.
2. Read the query. Skim `src/qaudit/kb/documents.json` (the passage ids and titles are enough once you know the KB).
3. Correct `relevant_passages` to the exact set an auditor would need. Add or remove ids.
4. Set `"reviewed": true` and, if useful, leave a `note`.

**Format.** `relevant_passages` is a list of passage `id` strings from the KB. Order does not matter.

## 2. Judge gold — `judge_gold.jsonl`

**Task.** For each conversation, give the correct verdict for **each of the five rubric criteria**: `pass`, `violation`, or `na` (not applicable). This is the human label the LLM-as-judge is validated against (Cohen's kappa).

**Verdicts.**
- `pass` — the response satisfies the criterion.
- `violation` — the response breaks the criterion (see each criterion's `violation_when` in `src/qaudit/rubric/criteria.json`).
- `na` — the criterion genuinely does not apply. Use sparingly. Mainly for `policy_accuracy` when the reply makes **no checkable factual/procedural claim** (a pure acknowledgement, or "let me check for you"). `intent_resolution`, `completeness` and `tone_empathy` are essentially always applicable.

**What counts as a VIOLATION, per criterion** (full text in `criteria.json`):

| Criterion | Violation when… |
|---|---|
| `intent_resolution` | answers a different or generic question, or ignores part of the request |
| `policy_accuracy` | states a step / timeframe / fee / eligibility rule that contradicts the KB, or invents one |
| `completeness` | a non-answer ("refer to the terms", "get in touch") with no concrete step, or omits the key detail |
| `tone_empathy` | curt, dismissive, or robotic toward a clear complaint / upset customer |
| `compliance_safety` | asks for a password / full card number / PIN / CVV in chat, leaks a third party's data, or promises an outcome policy doesn't allow |

**How to label.**
1. Open `judge_gold.jsonl`. Each line is one conversation with a `labels` object (`criterion_id -> verdict`).
2. Read the conversation. The text is in `data/conversations.jsonl` (real) and `data/synthetic.jsonl` (synthetic), keyed by `conversation_id`; or print it with
   `python -c "from qaudit.eval.runner import labelled_conversations as L; print({c.id:c.render() for c in L()}['conv-0007'])"`.
3. For `policy_accuracy`, check the claim against the KB passages, not your own assumptions.
4. Correct each verdict, set `"reviewed": true`, and note anything borderline.

**Synthetic rows (`"source": "synthetic"`).** These were built by injecting one known violation into a real response (see `qaudit.synth`). The `note` records which criterion was injected. Two things to confirm:
- the injected criterion really reads as a `violation` after the rewrite, and
- whether the rewrite *also* trips another criterion (e.g. an over-promise is both a `compliance_safety` and a `policy_accuracy` problem). The draft labels only the injected criterion to stay conservative; add the others if you agree they apply.

**Format.** One JSON object per line. Keep `conversation_id`, `source`, `intent`; edit `labels` and `reviewed`.

## Priorities if your time is limited

1. **The 9 draft violations** (2 real, 7 synthetic) — the rare class drives kappa and violation-F1 most, so confirm these first.
2. **Every `policy_accuracy` call** — the hardest and most subjective; the judge's biggest disagreements are here.
3. **The retrieval rows where BM25 and dense disagree** — those are where relevance precision matters most (`reports/retrieval_eval.md` after a run shows where they differ).
4. The remaining `pass` rows — mostly confirmations, quicker to sweep.
